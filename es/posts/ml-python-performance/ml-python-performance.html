1 Introducción

Uno de los errores más comunes al optimizar código ML es atacar el primer síntoma visible sin diagnosticar la causa real. Este apunte describe un flujo de diagnóstico sistemático para código Python con PyTorch/JAX, ilustrado con un caso real de análisis de performance del paquete U-TraCE corriendo sobre un Ryzen 5700G.

El principio guía es: medir antes de modificar. Cada decisión de optimización debería estar respaldada por evidencia del profiler, no por intuición.

2 El síntoma clásico: “solo la mitad de los cores están activos”

Al ejecutar código con paralelismo (JAX, Numba, OpenCL, PyTorch), es habitual observar en el monitor de sistema que solo la mitad de los procesadores lógicos aparecen activos. En un Ryzen 5700G (8 cores físicos + SMT = 16 lógicos), esto se manifiesta como 8 de 16 cores en uso.

2.1 Por qué ocurre: SMT y las bibliotecas de álgebra densa

Este comportamiento no es un bug — es una decisión de diseño deliberada de las bibliotecas de HPC. La razón es empírica: para cargas compute-bound (álgebra densa, kernels numéricos vectorizados), los dos hilos lógicos de un mismo core físico comparten las unidades de ejecución, la FPU, y las cachés L1/L2. SMT está diseñado para esconder latencias de memoria intercalando trabajo heterogéneo, no para duplicar throughput cuando ambos hilos ya saturan las ALU/FPU.

Hay un caso documentado[@openblas1881] en una máquina de 88 cores (44 físicos + HT) donde dejar a OpenBLAS usar todos los hilos producía un SVD en 11.9s, mientras que limitarlo a 44 hilos lo reducía a 3.29s — 3× más rápido con la mitad de hilos. El oversubscription genera contención en los recursos compartidos del core.

Por este motivo, Intel MKL, OpenBLAS, y la mayoría de los backends de álgebra densa defaultean a n_cores_físicos hilos, no a n_cores_lógicos.

2.2 Verificar el patrón con ps

# Ver cuántos hilos tiene el proceso
ps -o nlwp <pid>
# o equivalente:
ls /proc/<pid>/task/ | wc -l

# Ver qué hilos están corriendo (estado R) y en qué core lógico
ps -L -o pid,tid,psr,stat,pcpu,comm -p <pid> --no-headers | awk '$4 ~ /^R/'

# Ver distribución de estados
ps -L -o stat -p <pid> --no-headers | sort | uniq -c

Interpretación del output típico:

405961  405961  13 Rl+  98.5 python3    ← main thread (TID=PID)
405961  406031   2 Rl+  53.0 python3    ← worker 1
405961  406032  12 Rl+  53.0 python3    ← worker 2
...

Los flags de estado significan:

Flag Significado
R Running (en CPU o en runqueue)
S Sleeping (esperando futex/condición)
l Multi-threaded (el proceso tiene LWPs)
+ En el foreground process group de la terminal

Una distribución típica en JAX/PyTorch: pocos hilos en R, muchos en S. Los ~100 hilos dormidos son thread pools de Eigen, BLAS, OpenMP — esperando trabajo, no consumiendo CPU.

2.3 El scheduler de Linux y el SMT-awareness

Linux CFS (Completely Fair Scheduler) tiene awareness de la topología SMT: cuando tiene N hilos compute-bound con N ≤ cores físicos, los distribuye de forma que cada hilo ocupe un core físico completo, evitando que dos hilos hermanos SMT compitan entre sí.

En un Ryzen 5700G (Zen 3), Linux enumera los pares SMT como (cpu0, cpu8), (cpu1, cpu9), ..., (cpu7, cpu15). Si el scheduler asigna hilos a los cores 0, 2, 3, 6, 9, 12, 13, 15, estos corresponden a 8 cores físicos distintos — exactamente uno por par SMT.

# Verificar los pares SMT de tu hardware
for i in $(seq 0 15); do
  echo "cpu$i ↔ $(cat /sys/devices/system/cpu/cpu$i/topology/thread_siblings_list)"
done

Conclusión: ver la mitad de los cores lógicos activos es el comportamiento correcto y óptimo para cargas de álgebra densa.

3 Herramientas de diagnóstico: nivel sistema operativo

3.1 perf y perf_event_paranoid

perf es la herramienta canónica del kernel Linux para performance hardware. En sistemas con configuración de seguridad restrictiva (habitual en Debian y derivados), puede aparecer el error:

Access to performance monitoring and observability operations is limited.
perf_event_paranoid setting is 4

Los niveles de perf_event_paranoid son:

Valor Significado
-1 Acceso libre para todos los usuarios
0 Deshabilita acceso raw/ftrace
1 Deshabilita acceso a eventos de CPU
2 Deshabilita profiling del kernel
3-4 Extensiones de Debian/grsecurity (más restrictivo)

Los valores 3 y 4 no son parte del kernel mainline — vienen de parches de Debian/grsecurity y están presentes desde 2015 sin haber entrado a upstream.

Para análisis temporales sin riesgo de seguridad:

# Cambio temporal (hasta el próximo boot)
sudo sysctl kernel.perf_event_paranoid=1

# Verificar valor actual
cat /proc/sys/kernel/perf_event_paranoid

4 Profiling a nivel Python: py-spy

py-spy es un profiler de sampling para Python que no requiere modificar el código fuente y tiene overhead muy bajo (~1%). Es la herramienta más práctica para un primer diagnóstico.

4.1 Instalación y uso básico

# Instalar (con uv/pipx, preferible a pip global)
pipx install py-spy

# Modo top (interactivo, como htop)
sudo env "PATH=$PATH" py-spy top --pid <pid>

# El sudo es necesario para acceder al proceso de otro usuario
# env "PATH=$PATH" preserva el PATH del usuario (py-spy instalado en ~/.local/bin)
TipPor qué env "PATH=$PATH"

sudo resetea el PATH por defecto. Si py-spy está instalado con pipx o pip --user, queda en ~/.local/bin, que no está en el PATH de root. Pasar la variable explícitamente lo resuelve.

4.2 Leer el output de py-spy top

Collecting samples from 'python3 scripts/example.py'
Total Samples 500
GIL: 70.00%, Active: 94.00%, Threads: 1

  %Own   %Total  OwnTime  TotalTime  Function (filename)

Los tres indicadores de la cabecera son los más importantes:

GIL — porcentaje de muestras en las que algún thread Python sostenía el GIL ejecutando bytecode. Valores altos (>50%) indican que el código Python “puro” domina el wall-clock. El GIL es serial por definición: no escala con más cores.

Active — porcentaje de muestras en que el proceso hacía trabajo (incluyendo extensiones C/C++ que liberaron el GIL). Un valor cercano a 100% indica que el proceso no espera I/O significativo.

Threads — número de threads Python visibles para py-spy. Por defecto solo muestra threads que pueden sostener el GIL. Los threads nativos (Eigen, BLAS, OpenMP) son invisibles salvo que se use --native.

Las columnas de funciones:

Columna Significado
%Own Muestras donde la función está en el top del stack (costo propio)
%Total Muestras donde la función aparece en cualquier posición del stack
OwnTime Tiempo acumulado desde inicio del profile (no la ventana reciente)
TotalTime Ídem para la función y sus callees
Warning%Own/%Total vs OwnTime/TotalTime — inconsistencia aparente

Los porcentajes se calculan sobre una ventana reciente (como top), mientras que los tiempos son acumulativos desde el inicio. Una función con %Own=0.00% pero OwnTime=2.75s fue caliente al principio del profile y ya no lo es — su tiempo acumulado se preserva aunque no esté activa ahora. Esto hace que las filas parezcan inconsistentes; no lo son.

5 El GIL y su impacto en ML

5.1 Diagnóstico: GIL alto al inicio (70%)

El primer profile del caso de estudio mostraba:

GIL: 70.00%, Active: 94.00%, Threads: 1

Con GIL=70% y Active=94%, el reparto aproximado es:

  • 70% Python serial (bajo el GIL)
  • 24% C++ multi-threaded (liberó el GIL)
  • 6% idle

El call stack dominante apuntaba a __getitem__ del dataset MNIST, to_tensor y normalize de torchvision — operaciones de preprocessing corriendo en el main thread, bajo el GIL, en serie.

Diagnóstico: los DataLoaders tenían num_workers=0 (modo síncrono). Todo el preprocessing bloqueaba el thread principal antes de cada forward pass.

5.2 Solución: num_workers > 0

# Antes (síncrono, GIL 70%)
loader = DataLoader(dataset, batch_size=64, num_workers=0)

# Después (asíncrono, GIL ~0%)
loader = DataLoader(dataset, batch_size=64, num_workers=4)

Con num_workers=4, los DataLoaders lanzan 4 procesos worker independientes que precargan los batches. El efecto en el profile fue inmediato:

Métrica num_workers=0 num_workers=4
GIL 70% 0%
Active 94% 100%
Threads (Python) 1 2

Las funciones de transforms desaparecieron del top. Aparecieron en su lugar funciones de IPC de multiprocessing (_feed, _recv, _launch) con tiempos acumulados de ~0.36s sobre 280s de wall-clock — 0.13% del tiempo total. El overhead de la comunicación entre procesos es despreciable.

5.3 Importante: GIL alto ≠ 70% del wall-clock

GIL=70% significa “en el 70% de las muestras, algún thread Python sostenía el GIL”. No significa que el 70% del tiempo de reloj lo consume Python. Como el data loading bajo el GIL puede ocurrir en overlap con las convoluciones (que liberan el GIL), el impacto real puede ser mucho menor. Cuantificarlo requiere medir wall-clock con y sin la optimización.

6 CPU pulsado: barreras de sincronización por mini-batch

Después de mover a num_workers=4, el gráfico de uso de CPU seguía siendo irregular: picos al ~70% seguidos de valles al ~20%, con una frecuencia de ~30-40 ciclos en 60 segundos.

6.1 Diagnóstico del patrón pulsado

Este patrón es típico de una barrera de sincronización por mini-batch. La hipótesis principal:

  • Pico (~70%): forward pass ejecutando convoluciones y matmuls multi-thread
  • Valle (~20%): main thread bloqueado esperando el próximo batch o ejecutando fases Python/JAX seriales entre batches

6.2 Cómo medir los valles con precisión

Opción 1 — cronómetros manuales (recomendado como primer paso):

import time

t_prev = time.perf_counter()
for i, (x, y) in enumerate(loader):
    t0 = time.perf_counter()
    out = model(x)
    t1 = time.perf_counter()
    loss = criterion(out, y)
    t2 = time.perf_counter()

    if i % 20 == 0:
        print(f"step {i:4d} | wait={t0-t_prev:.3f}  fwd={t1-t0:.3f}  loss={t2-t1:.3f}")
    t_prev = t2

wait mide exactamente cuánto tiempo el main thread esperó entre el fin del step anterior y la disponibilidad del próximo batch.

Opción 2 — py-spy con formato speedscope (preserva eje temporal):

py-spy record --format speedscope -o profile.json --pid <pid>
# Abrir en https://www.speedscope.app

Opción 3 — aliasing del monitor de sistema

GNOME System Monitor muestrea a ~1Hz. Si el período real de iteración es del orden de 200-500ms (común en inferencia con MNIST), el monitor puede mostrar envolventes lentas que no reflejan la frecuencia real. Para descartarlo:

# Muestreo a 10Hz durante 30 segundos
while true; do
  awk '/^cpu / {u=$2+$3+$4; t=u+$5; printf "%.1f\n", u/t*100}' /proc/stat
  sleep 0.1
done | head -300

Si con mayor frecuencia de muestreo el patrón desaparece, era un artefacto visual.

7 El bottleneck real: arquitectural

Después de resolver el data loading, el profile apuntaba a tres kernels C++ de PyTorch consumiendo ~99% del wall-clock:

_conv_forward    188.0s   (68%)
relu              72.3s   (26%)
forward (Linear)  14.4s   ( 5%)

En el caso de U-TraCE, el análisis del código fuente reveló un bottleneck más grave que el threading: el forward pass del modelo se recomputaba ~51 veces más de lo necesario por nivel de noise.

7.1 Cómo identificar recomputación innecesaria

La señal en el code review es la presencia del mismo método de inferencia (predict_proba, forward, etc.) en múltiples loops anidados que operan sobre los mismos datos:

# Patrón problemático: mismos datos, múltiples loops → múltiples forwards
for noise in noises:                    # loop externo
    for C in classes:                   # loop por clase
        for X, y in dataloader:         # loop por batch
            probs = model(X)            # ← forward recomputado aquí
            scores = uq.calibrate(probs, y)
    
    for C in classes:                   # segundo loop sobre los mismos datos
        for X, y in dataloader:
            probs = model(X)            # ← mismo forward, de nuevo
            scores = uq.get_uncertainty(probs, y)

La solución: separar la inferencia del modelo del cómputo de métricas. Hacer un único forward pass sobre cada split del dataset, guardar los logits/probabilidades, y pasarlos a todas las funciones de análisis que los necesiten.

# Patrón eficiente: un único forward pass, reutilización de outputs
all_probs = {split: model(X_split) for split, X_split in splits.items()}

for noise in noises:
    for C in classes:
        scores = uq.calibrate(all_probs['cal'], y_cal)
        scores = uq.get_uncertainty(all_probs['test'], y_test)

8 Flujo de diagnóstico recomendado

1. Observar síntoma
   └─ ¿Solo la mitad de los cores activos?
      → Normal para álgebra densa. Verificar con ps.
   └─ ¿Proceso lento de forma inexplicable?
      → Continuar con paso 2.

2. py-spy top (visión general)
   ├─ GIL alto (>50%) → bottleneck Python serial
   │   └─ ¿Transforms en el main thread? → num_workers > 0
   │   └─ ¿Otra función Python dominante? → revisarla
   ├─ GIL bajo, Active alto → C++ multi-threaded dominando
   │   └─ py-spy no ayuda más → ir a paso 3
   └─ Active bajo → el proceso espera (I/O, locks)
       └─ strace, lsof, o instrumentar con time.perf_counter()

3. Cronómetros manuales (si CPU pulsado)
   └─ Medir wait/fwd/loss/bwd por iteración
   └─ Identificar qué fase genera los valles

4. Code review para recomputación
   └─ ¿El mismo forward pass aparece en múltiples loops sobre los mismos datos?
   └─ ¿Se están cachando los logits/probabilidades entre fases?
